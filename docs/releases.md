# 自动发布

推送到 `main` 后，Release Plugin 工作流按主线顺序逐一构建尚未发布的非文档提交。一次推送包含多个提交或构建期间收到新提交时，每个非文档提交分别出包。仅修改 Markdown（`.md` / `.mdx`）或 `docs/` 下文档及资源的提交不出包、不占版本序号；与代码或打包配置混合修改时正常出包。自动版本提交不会再次发包。手动运行工作流可以续跑未完成的队列，无需指定版本。

版本为 `YYYY.M.D.N`，日期使用北京时间，每天首包为 `.0`，同日按已有 tag 的最大尾号加一（`.9` 后为 `.10`）。tag 带 `v`，清单版本不带。旧 tag 和 Release 保留，不覆盖旧包；失败后已分配的 tag 不复用，因此序号可能有间隔。若同日已有旧三段日期版本，则从 `.1` 开始，避免 `.0` 被判为相同版本；系统日期早于当前版本日期时沿用当前日期前缀，避免降级。

首次启用的历史边界为 `80979bd6f604ab915ddf64a285164e7bfa0124ec`（工作流 `RELEASE_BASE_SHA`），不补发此前历史提交，也不将其伪记为已发布。首次成功后由 `plugin.json.releaseSource` 记录真实发布进度，后续运行优先使用它；不要随意修改边界或进度。

每个包在独立 Git worktree 中依次完成冻结依赖安装、后端/前端类型检查、全部测试、构建与清单校验，并确认原生/Web bundle 和 HTML 回退入口均存在。tag 指向对应源码提交加版本元数据的快照。Release 说明的 `Source commit` 与 `plugin.json.releaseSource` 记录原始源码 SHA；主线自动版本提交同步版本、下载地址和包哈希。无需手动打 tag 或运行本地发布命令。

检查失败会停止队列，后续从失败提交继续；需恢复相应构建条件再重跑。发布成功但主线元数据推送失败时，重跑接回该提交已有 Release，不重复构建发布。工作流串行排队，运行中会重新拉取主线，避免并发版本冲突及漏发。

本地验证：

```bash
node --test tests/release_pipeline.test.mjs
pnpm test
```

发布测试使用临时本地 Git 远端与模拟 GitHub Release，不向真实仓库发布。覆盖跨日、数字尾号、旧版本迁移、首次启用边界、批量提交、构建期间的新提交、纯文档跳过、失败续跑、发布后元数据写入失败、tag/源码对应关系与双端产物闸门。
